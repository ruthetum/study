# Orca 활용 가이드 — 주요 기능·장단점·사용법·팁

작성일: 2026-09-20  
대상 제품: [Orca ADE](https://www.onorca.dev/), [stablyai/orca](https://github.com/stablyai/orca)

## 1. 어떤 도구인가

Orca는 여러 코딩 에이전트를 작업 단위로 나눠 운영하는 데 초점을 둔 개발 환경이다. Worktree, 에이전트 터미널, 편집기, 브라우저, 변경사항 리뷰를 연결한다. macOS·Windows·Linux용 오픈소스 제품이며 MIT 라이선스로 안내한다. 별도의 AI 모델이 아니므로 실제 추론은 연결한 에이전트·공급자의 기능과 이용 조건에 따른다. [공식 소개](https://www.onorca.dev/docs)

**추천 대상:** 에이전트가 만든 코드와 문서를 직접 읽고, UI를 확인하고, 수정 지시를 반복하는 개발자.  
**도입 효과가 작은 경우:** 하나의 에이전트만 사용하고 현재 IDE·터미널 전환에 불편함이 없는 경우.

이 문서는 제공 영상의 경험담과 현재 공식 문서를 구분한다. 직접 설치·성능 측정은 하지 않았으며, 아래 프롬프트와 프로젝트 운영 팁은 작성자의 제안이다. 영상 중 `T9mypKihAeY`는 설명란·챕터만 확인했다.

## 2. 주요 기능

| 기능 | 활용 목적 | 사용 시 확인할 점 |
|---|---|---|
| Git worktree 중심 작업 | 기능별 브랜치·디렉터리 분리 | 개발 DB·서버 포트까지 자동 분리되는 것은 아님 |
| 여러 CLI 에이전트 | 서로 다른 모델·도구로 구현·검토 | 각 CLI 설치·인증·이용 한도 |
| 편집기·파일 탐색기 | 코드·문서를 읽고 가벼운 수정 | 기존 IDE의 언어별 도구·확장과 동일하지 않음 |
| Diff 코멘트 | 수정 위치와 근거를 모아 에이전트에 피드백 | 최종 커밋의 변경 내용을 다시 확인 |
| 작업별 브라우저·Design Mode | 웹 UI의 특정 요소를 지정해 수정 | 네이티브 앱 UI 검증과 구분 |
| CLI·스킬·오케스트레이션 | 에이전트가 작업 생성·분배·회수를 수행 | 현재 앱과 맞는 스킬·명령 확인 |
| 모바일 companion | 상태 확인, 짧은 응답, 코드 변경 검토 | 실행 호스트 연결 및 모바일 베타 제약 |
| SSH·원격 작업 | 원격 자원에서 실행하고 로컬에서 관리 | 실행 머신의 의존성·경로·접속 설정 |
| 세션 유지·복원 | 앱 재실행 때 작업 맥락 복구 | 데몬 유지와 머신 재부팅을 구분 |
| 사용량·작업 관리 연동 | 한도·이슈·리뷰 맥락 확인 | 공급자·연동별 지원 범위 |

기능 목록 근거: [제품 기능](https://www.onorca.dev/), [공식 문서 목차](https://www.onorca.dev/docs), [CLI 개요](https://www.onorca.dev/docs/cli/overview).

## 3. 장점과 단점

| 장점 | 실제로 편해지는 일 |
|---|---|
| 작업·코드·미리보기가 가까이 있음 | 터미널 출력 확인 후 파일·diff·브라우저를 오가는 부담 감소 |
| Worktree를 기본 단위로 사용 | 여러 에이전트에게 독립 구현이나 대안 실험을 맡기기 쉬움 |
| 위치를 지정하는 피드백 | 긴 설명 대신 diff 줄이나 웹 요소를 기준으로 요청 가능 |
| 협업 계층 제공 | 일회성 터미널 입력보다 작업·완료·질문을 구조적으로 관리 가능 |
| 모바일 접점 | 짧은 질문 때문에 에이전트가 오랫동안 대기하는 상황을 줄일 여지 |

| 단점·비용 | 대응 방법 |
|---|---|
| GUI·브라우저·에이전트·개발 서버가 함께 자원을 사용 | 처음에는 worktree 2개로 시작하고 메모리 압박과 리뷰 대기량을 관찰 |
| 전문 IDE 기능의 대체 범위가 제한적 | Kotlin/Spring 디버깅·리팩터링 등은 익숙한 IDE를 함께 사용 |
| 업데이트가 빨라 메뉴·CLI가 달라질 수 있음 | 영상 명령을 복사하기 전 설치 버전의 스킬을 조회 |
| 오케스트레이션 설정만으로 좋은 분업이 생기지 않음 | 수정 영역·의존성·검증·종료 기준을 명시 |
| 여러 결과를 만들면 검토 비용도 증가 | 대안 구현은 중요한 설계 문제에만 사용 |

리소스·편집기·초기 안정성에 대한 경험담은 [Orca 핵심 가이드](https://www.youtube.com/watch?v=QqLInsPlt4Y)와 [Orca/Herdr 비교](https://www.youtube.com/watch?v=VgngB-ZF8ac)에 나온다. 위 대응 방법은 실무 제안이다. **RAM을 몇 배 더 사용한다는 식의 수치 비교는 근거가 없어 제시하지 않는다.**

## 4. 처음 사용하는 순서

### 4.1 설치 및 에이전트 확인

macOS에서 Homebrew를 사용한다면 공식 저장소가 안내하는 명령은 다음과 같다.

```bash
brew install --cask stablyai/orca/orca
```

다른 OS는 [공식 다운로드](https://www.onorca.dev/)에서 해당 플랫폼 빌드를 선택한다. [설치 출처](https://github.com/stablyai/orca)

에이전트 CLI가 이미 설치되어 있다면 기존 터미널에서 먼저 정상 실행·인증되는지 확인한다. Orca에서 에이전트가 인식되더라도 모델 사용 권한이나 이용 한도가 새로 생기는 것은 아니다.

### 4.2 저장소와 첫 작업 만들기

1. `Add Repo`로 로컬 Git 저장소를 추가한다.
2. 기본 브랜치가 새 작업의 기준으로 올바른지 확인한다.
3. 작은 기능 또는 버그 하나로 작업을 생성한다.
4. 해당 작업에서 사용할 에이전트를 실행하고 수정 범위·완료 기준을 전달한다.
5. 두 번째 작업은 첫 작업과 독립적인 내용으로 만든다.

기본 흐름은 [첫 세션 가이드](https://www.onorca.dev/docs/first-session)를 따른다. 화면 구성은 설치 버전에 따라 달라질 수 있다.

### 4.3 Worktree를 정확히 이해하기

Worktree는 같은 저장소의 별도 작업 디렉터리다. 브랜치별 파일 변경을 분리하는 데 유용하지만 머신·네트워크·외부 서비스의 격리 환경은 아니다. [공식 Worktrees](https://www.onorca.dev/docs/model/worktrees)

예를 들어 `calendar-ui`와 `sqlite-migration` 두 작업을 분리해도 같은 앱 DB 파일, 동일한 개발 서버 포트, 공용 환경설정을 사용하면 실행 과정에서 간섭할 수 있다. 따라서 작업 시작 시 **파일 격리와 실행 자원 격리**를 각각 확인한다.

### 4.4 결과 확인과 피드백

작업이 끝나면 변경사항을 열고 문제가 있는 위치에 코멘트를 남긴다. 여러 코멘트를 모아 에이전트에 전달하는 기능이 제공된다. [Annotate AI Diff](https://www.onorca.dev/docs/review/annotate-ai-diff)

좋은 코멘트의 예:

```text
이 분기는 만료된 일정과 사용자가 완료 처리한 일정을 구분하지 못합니다.
기준시각은 서버 응답의 asOf를 사용하고, expiry == asOf 경계도 확인해주세요.
빈 배열 응답과 API 실패 응답의 UI 처리도 분리해주세요.
```

코멘트는 원하는 결과와 판단 근거를 함께 쓴다. “깔끔하게 고쳐줘”보다 검증 가능한 요구가 효과적이다.

## 5. Design Mode 활용

작업의 내장 브라우저에서 개발 페이지를 열고 Design Mode로 요소를 선택한다. 선택한 요소의 정보를 에이전트에 전달해 수정할 수 있다. [Design Mode](https://www.onorca.dev/docs/browser/design-mode)

권장 순서:

1. 수정할 페이지·화면 크기를 명확히 한다.
2. 문제 요소를 선택하고 기대 간격·정렬·동작을 설명한다.
3. 반영 후 동일한 상태에서 다시 확인한다.
4. 인접 화면·긴 텍스트·빈 상태에서도 깨지지 않는지 점검한다.

**RN 적용 팁:** Expo Web 등 웹으로 렌더링한 화면은 웹 점검에 활용할 수 있다. 이 결과만으로 iOS safe area, Android 키보드, 권한 요청, 공유 확장, 로컬 알림이 검증되었다고 판단하지 않는다. 이는 제품 기능과 네이티브 플랫폼의 검증 범위를 구분한 제안이다.

## 6. CLI와 스킬

현재 공식 문서는 `Settings → General → Orca CLI`에서 CLI를 등록하도록 안내한다.

```bash
command -v orca
orca status --json
orca worktree ps --json
orca terminal list --json
```

기본 CLI 스킬 설치 예:

```bash
npx skills add https://github.com/stablyai/orca --skill orca-cli
```

출처: [CLI 개요](https://www.onorca.dev/docs/cli/overview). 스킬은 에이전트가 Orca를 다루도록 돕는 사용 지침이며, 앱·CLI·인증 설정을 모두 대신하는 것은 아니다. 추가 스킬은 [스킬 레지스트리](https://www.onorca.dev/docs/cli/skills)에서 확인한다.

## 7. 오케스트레이션 사용법

### 7.1 현재 구조

현재 공식 문서에서는 Experimental 설정을 켠 뒤 Run, Task, Dispatch, worker, 메시지, decision gate를 사용한다. Run은 실행을 묶는 공간이며 스스로 작업을 배치하는 스케줄러가 아니다. 실제 조정자가 다음 작업과 실패 처리를 결정한다.

과거 `orca orchestration run` 등 일부 명령은 폐기되었다. 실행 전에 설치 버전의 안내를 읽는다.

```bash
orca status --json
orca skills get orchestration --full
```

완료 보고에는 현재 작업·시도에 해당하는 식별자를 사용해야 한다. 오래된 재시도의 완료 메시지를 현재 시도의 성공으로 받아들이지 않도록 하는 구조다. [공식 오케스트레이션](https://www.onorca.dev/docs/cli/orchestration)

### 7.2 처음에는 자연어로 작게 지시하기

아래는 복사해 수정해서 사용할 수 있는 **제안 프롬프트**다. 스킬 호출 표기는 에이전트별 UI에서 확인한다.

```text
설치된 Orca orchestration 스킬을 사용해 이 작업을 관리해주세요.

목표: 캘린더에서 만료 일정이 노출되는 버그 수정.
먼저 현재 구현과 요구사항을 확인하고, 범위가 불명확하면 보고해주세요.

역할:
- 구현 담당: 별도 worktree에서 필터링 로직과 관련 테스트 수정.
- 검토 담당: 읽기 전용으로 기준시각·경계값·완료 상태와의 차이를 검토.
- 총괄: 결과를 취합하고 하나의 작업 브랜치에 통합.

제약:
- 동시에 수정하는 담당자는 같은 파일을 공유하지 않음.
- 스키마·의존성 변경이 필요하면 이유와 대안을 먼저 보고.
- 재작업은 최대 2회. 해결되지 않으면 실패 원인과 재현 절차를 남김.

완료 기준:
- 지정된 회귀 테스트 통과.
- 변경 파일, 실행한 검증, 미검증 항목을 보고.
- 최종 결과는 검토 가능한 diff와 보고서로 제시.
```

### 7.3 그래프형 작업에서 꼭 정할 항목

- 선행 작업의 성공을 확인한 뒤 후속 작업을 시작한다.
- 결과물 경로와 형식을 고정한다.
- 실패·사용자 질문·시간 초과를 성공과 구분한다.
- 반려 시 전부 재실행할지 실패 단계만 재실행할지 정한다.
- 최종 통합 담당자는 한 명으로 둔다.

영상의 블로그 요약·초안·검토 루프는 이런 관계를 설명하는 좋은 예다. 다만 실습의 논리적 이름 `T1` 등을 실제 런타임 ID로 가정하지 않는다. [그래프 엔지니어링 영상](https://www.youtube.com/watch?v=-pk2umNC-18)

## 8. 모바일과 지속성

모바일 앱은 실행 호스트를 원격으로 확인·조작하는 companion이다. 현재는 iOS 앱과 Android APK를 안내하며 베타로 표기한다. 데스크톱에서 페어링 코드를 만들고 앱에서 연결한다. Relay와 LAN 경로를 구분하고, 선택한 경로로 호스트에 도달할 수 있어야 한다. Relay에만 로그인 요구가 있다. [공식 모바일 가이드](https://www.onorca.dev/docs/mobile)

현재 Orca는 별도 데몬을 통해 일반적인 앱 종료 후에도 에이전트 프로세스를 유지한다. 그러나 호스트 재부팅·전원 차단·데몬 종료 시 실행 프로세스는 사라진다. 다음 실행에서 레이아웃이 돌아오는 것과 프로세스가 계속 실행된 것은 다르다. [공식 세션 복원](https://www.onorca.dev/docs/model/session-restore)

**실무 팁:** 모바일 응답이 필요하다면 자리를 비우기 전에 실제 사용할 외부 네트워크에서 연결을 시험한다. 앱 종료 후 작업은 살아 있어도 모바일 연결은 끊어질 수 있으므로 두 가지를 따로 확인한다. 큰 코드 리뷰는 책상에서 하고, 모바일에는 간단한 질문 응답·진행 확인을 맡기는 편이 좋다.

## 9. 프로젝트 운영 팁

### Kotlin/Spring

- IntelliJ를 심층 디버깅·리팩터링 용도로 유지한다.
- Worktree마다 서버 포트와 개발용 DB/schema를 구분한다.
- Redis key prefix와 Kafka consumer group을 분리해야 하는지 확인한다.
- 멀티모듈 의존성 변경은 통합 담당자에게 모은다.
- 배치 개선은 happy path 외에 재시도·백필·중복 실행 결과를 요구한다.

### RN·Expo

- 하나의 변경을 확인하는 기준 시뮬레이터·Metro 서버를 명시한다.
- 네이티브 의존성이나 공유 확장을 여러 에이전트가 동시에 바꾸지 않게 한다.
- UI 완료와 iOS·Android 실행 검증 완료를 별도 항목으로 관리한다.
- 디자인 수정은 스크린샷뿐 아니라 로딩·빈 결과·오류·만료 상태도 전달한다.

### 비용과 작업량

Orca 앱이 무료라는 사실과 연결한 모델의 이용 비용은 구분한다. 한 문제를 세 에이전트에게 동시에 풀게 하면 대안을 얻지만 검토할 결과와 모델 사용량도 늘어난다. 처음에는 구현 1개와 검토 1개로 시작해 추가 병렬화가 실제 재작업을 줄이는지 확인한다.

위 항목은 제품의 자동 보장 기능이 아닌 운영 제안이다.

## 10. 자주 막히는 상황

| 증상 | 먼저 확인할 것 |
|---|---|
| `orca`를 찾지 못함 | CLI 등록 여부와 새 터미널의 PATH |
| 에이전트가 시작되지 않음 | 해당 CLI가 원래 터미널에서 실행·인증되는지 |
| 스킬 호출이 보이지 않음 | 선택한 에이전트에 스킬이 설치되었는지, 세션 재시작이 필요한지 |
| 오케스트레이션 명령이 작동하지 않음 | Experimental 설정, 런타임 연결, 설치 버전 스킬과의 일치 |
| 에이전트는 완료했는데 결과가 없음 | 산출물 경로, 작업 ID, 실패 메시지, 검증 실행 여부 |
| 모바일 연결만 끊김 | 데스크톱·Relay 연결과 네트워크 도달성 |
| 브라우저에 다른 작업의 앱이 보임 | 개발 서버 포트·현재 worktree·페이지 주소 |
| 메모리가 빠르게 증가 | 열린 브라우저·개발 서버·활성 에이전트·worktree 수 |

첫 주의 목표는 “기존 IDE를 전부 대체”가 아니라 **작업 전환과 피드백 전달 시간을 줄였는지 확인**하는 것이다.
